## 一、结论摘要

现状中最典型的问题接口是 **`POST /journeys/plan/save`（全量覆盖式）**，它导致"新增一个地点 = 把整个计划（places 全量数组 + budgetEstimate）整包重传"。

**根因不是设计选择，而是前后端契约脱节**：

- 前端 [mini/src/api/plan.ts](../../../mini/src/api/plan.ts) 早已声明单点接口 `planApi.placeUpsert`（`POST /journeys/plan/place/upsert`）与 `planApi.placeDelete`（`POST /journeys/plan/place/delete`），注释明确写着"请求体只带这一个地点，不整包提交整个计划"；
- 但后端 **从未实现这两个路由**（全库无 `place/upsert`、`place/delete` 注册）；
- 前端 [mini/src/stores/plan.ts](../../../mini/src/stores/plan.ts) L254/L268 每次调用都 404 → 进入 `catch` → `enqueuePlanFull(journeyId)` **静默降级为全量 `plan/save`**。

于是线上实际行为就是用户所见：新增一个地点提交的是整个计划数组，请求体里看不出"这次加了什么"。

## 二、扫描范围与方法

- 后端：`src/modules/**/*.controller.ts` 全部 POST 写端点 + 对应 DTO（`journey.dto.ts` / `journey-api.dto.ts` / `recording.dto.ts` / `checklist.dto.ts` / `media.dto.ts` / `draft.dto.ts` 等）+ 服务层实现（`putPlan` / `patchPlan` / `syncBatch` 等）。
- 前端：`mini/src/api/*.ts`、`mini/src/stores/plan.ts`、`mini/src/lib/outbox.ts` 的实际调用点，用于核对契约是否一致（**凡前端调了而后端没有 = 契约脱节**，本次发现 1 处：plan 单点接口）。
- 判定标准：写接口按四种模式分类——
  - **A. 独立单点**：一次只新增/修改一个子资源，请求体只有该子资源 + 关联键（journeyId/ownerId 等），服务端内部做关联/联动。
  - **B. 全量覆盖**：把某个子资源集合整体提交，服务端 diff 合并（增改删都靠"全量 vs 现状"推断）。
  - **C. 批量幂等 upsert**：一次提交多条自包含对象，按 clientId 幂等 upsert（每条对象本身是全量）。
  - **D. 全量快照**：语义上本来就是整份文档的快照（如草稿）。

## 三、全部写接口现状总表

| 接口 | 语义 | 模式 | 请求体形态 | 评价 |
|---|---|---|---|---|
| `POST /journeys/create` | 新建旅程 | A/B 混合 | 旅程字段 + 内嵌 `destinations[]`（预定点） | 创建父资源时批量子资源属一次性初始化，可接受；但预定点后续增删仍走全量 plan（见下） |
| `POST /journeys/update` | 更新旅程 | A（单资源 patch） | 旅程字段 | ✅ 独立单点，无问题 |
| `POST /journeys/status` / `finish` | 状态流转 | A | 状态字段 | ✅ |
| `POST /journeys/delete` | 删除旅程 | A | `{id}` | ✅ |
| `POST /journeys/plan/save` | **计划整体保存** | **B. 全量覆盖** | `journeyId + places[]（全量）+ checks[] + budgetEstimate` | ❌ 本审计核心问题，见 §四 |
| `POST /journeys/plan/patch` | 计划部分更新 | B'（伪 partial） | `places?` 传入即全量替换 | ❌ 与 save 相同问题 |
| `POST /journeys/plan/toggleCheck` | 勾选准备事项 | A | `journeyId + checkId` | ⚠️ 已废弃（deprecated），真源为 checklist；仍挂在 plan 模块属职责混用 |
| `POST /journeys/checklist/create` | **新增准备事项** | **A. 独立单点** | `journeyId + {title, isDefaultChecked, remindBeforeDays}` | ✅ 正面范例 |
| `POST /journeys/checklist/reorder` | 排序 | 全量有序数组 | `journeyId + items[{id, sortOrder}]` | ✅ 排序语义下全量合理 |
| `POST /checklist/update` / `toggle` / `delete` | 事项更新/勾选/删除 | A | `{id, ...patch}` | ✅ |
| `POST /journeys/entries/sync` | 批量同步记录 | **C. 批量 upsert** | `entries[]`，每条全量字段（content/type/recordedAt/geo/media/expenses/voice 等） | ⚠️ 承载"新增+更新"双语义，见 §五.1 |
| `POST /journeys/:id/entries/sync` | 同上（旧路径） | C | 同 | ⚠️ 兼容双路径 |
| `POST /journeys/entries/delete` | 删除记录 | A | `{journeyId, clientIds[]}` | ✅ |
| `POST /records/update` | 更新单条记录 | A（patch） | `{id, ...patch}` | ✅ 独立单点 |
| `POST /records/delete` / `records/time` | 删除/改时间 | A | 单资源 | ✅ |
| `POST /media/prepare` | 上传前登记 | **A. 独立单点 + 关联** | `ownerType + ownerId + kind/mime/size`（ownerId 可选，confirm 时补） | ✅ 正面范例（先建媒体、后关联归属，两段式） |
| `POST /media/confirm` | 上传后确认关联 | A | `mediaId/confirmToken + ownerId?/entryId?` | ✅ |
| `POST /journeys/guide/create` | 生成游记 | A | `journeyId + templateId` | ✅ 独立单点 |
| `POST /journeys/guide/favorite` | 收藏游记 | A | `{journeyId, guideId?, isFavorited}` | ✅ |
| `POST /drafts/save` | 保存草稿 | **D. 全量快照** | `kind + payload（整份草稿）+ journeyId?` | ✅ 草稿即快照，全量语义正确 |
| `POST /drafts/delete` | 删除草稿 | A | `{id}` | ✅ |
| `POST /shares` | 创建分享 | A | `journeyId/guideId + channel` | ✅ 关联式 |
| `POST /invite/accept` | 接受邀请 | A | 单点 | ✅ |
| `POST /me/locations/clear`、`/journeys/locations/clear` | 清空足迹 | A（批量删除） | 空体 | ✅（位置归属记录，不单独新增） |
| `POST /profile/update` | 更新资料 | A | 字段 | ✅ |

**模式分布**：A 独立单点 = 绝大多数；B 全量覆盖 = 仅 plan/save、plan/patch 两处（正是问题所在）；C 批量 upsert = entries/sync；D 快照 = draft/save。

## 四、重点问题：plan/save 全量覆盖式

### 4.1 现状证据链

1. **后端入参**（`journey.dto.ts` `UpsertPlanDto`）：`places[]`（每个地点 10+ 字段）、`checks[]`、`budgetEstimate`，全部可缺省，**没有"只新增一个地点"的入口**。
2. **服务端 diff 合并**（`journey.service.ts` `putPlan` → `mergePlacesByClientId`）：拿请求全量数组与现存数组按 clientId 合并 → 推断出 新增/更新/删除 → 落库 → 联动删除占位记录（`prunePlanPlaceEntries`，上一轮刚加的联动逻辑就长在这里）。
3. **前端实际调用**：`stores/plan.ts` 的 `pushPlaceRemote`（单点新增）→ `planApi.placeUpsert` → **404** → `catch` → `enqueuePlanFull` → `planApi.put` → 全量 `plan/save`。单点删除同理走 `pushPlaceDeleteRemote` → 404 → 全量。
4. 全量排序/预算等整体状态场景前端确实有 `pushRemote`（`planApi.put` 全量）——这是合理的全量使用场景，但它与"单点增删"被降级混在了一起。

### 4.2 全量覆盖式的具体问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | **请求体不可读**：提交的是整个 places 数组，看不出本次新增/删除了哪个点；排查"用户加了什么"要 diff 服务端旧数据 | 不好维护、不好直观看到提交内容（用户原话） |
| 2 | **404 静默降级**：前端单点调用失败后无感知走全量，异常被吞掉，前后端都以为走的是单点路径 | 契约假象，掩盖真实网络/权限错误 |
| 3 | **并发覆盖**：全量数组整体替换，两端同时编辑时后提交者覆盖先提交者的改动，diff 也无法缓解 | 数据丢失风险 |
| 4 | **匿名 id 漂移**：无 clientId 的历史地点被服务端合成 `p_anon_{index}`，重排/新增时下标变化即身份变化，diff 误判为删除+新增 | 数据错乱、联动误删占位记录的隐患 |
| 5 | **职责混载**：同一个 save 同时承载 places（真源）、checks（已废弃双写）、budgetEstimate，三者生命周期不同 | 一处改动影响全局，`plan/toggleCheck` 已废弃却仍可写 checks |
| 6 | **联动逻辑耦合**：删点→删占位记录是"计划删除"的副作用，却只能寄生在"全量保存"的 diff 结果里，无法被单点删除路径复用 | 后续无论谁加单点接口都得重写一遍 diff |

## 五、次级关注点

### 5.1 `POST /journeys/entries/sync`：批量 upsert 双语义

- 前端 outbox 把本地全量记录数组整体上传，服务端按 clientId 幂等 upsert（新增/更新靠"同 clientId 存在与否"区分），删除走独立 `entries/delete`。
- 评价：记录本身是自包含业务对象（内容+媒体+花费+位置+语音），每条全量字段可接受；且**已有独立删除接口**，比 plan 模块规范。
- 可改进点（非必须）：新增语义可收敛为 `entries/create` 单条接口（只传关联键 journeyId + 该条记录），sync 只保留给离线批量回传场景；两者可以共存（create 实时、sync 兜底），但需防止双写乱序。

### 5.2 花费（expense）没有独立新增接口

- 现状：`expense` 模块只有统计/汇总接口（`expense/summary`），**新增花费只能内嵌在记录对象里**（entries/sync 的 `expenses[]` 或 records/update 的 patch）。
- 影响：如果产品存在"给旅程单独记一笔花费/预算"（不依赖某条记录）的入口，当前无接口可用；若花费严格从属于记录，则现状合理，维持即可。

### 5.3 `POST /journeys/create` 内嵌预定点

- 创建旅程时一次传入 `destinations[]`（预定点）属初始化场景，可接受；但创建后这些点与 plan 模块的 places 的关系需要说清（二者是否同源、create 是否也播种占位记录），避免"创建时一种路径、之后走 plan/save 另一种路径"的割裂。

## 六、正面范例（新增接口应有的样子）

| 接口 | 设计 | 可借鉴点 |
|---|---|---|
| `POST /journeys/checklist/create` | 请求体 = `journeyId + 单条事项字段` | 新增单点、关联键最小化、返回单条实体 |
| `POST /media/prepare` + `confirm` | 先建媒体（可无 ownerId），confirm 时补关联 | 新增与关联分离，两段式不阻塞上传 |
| `POST /journeys/guide/create` | `journeyId + templateId`，内部做校验/派生 | 只传关联键，服务端负责全部派生逻辑 |
| `POST /journeys/entries/delete` | `{journeyId, clientIds[]}` | 删除独立成接口，不与同步混用 |

## 七、改造方向（仅建议，未实施）

1. **补齐单点接口**（后端实现前端已声明的契约）：
   - `POST /journeys/plan/place/upsert`：请求体 = `journeyId + place（单地点，含 clientId）`，幂等按 clientId upsert，返回完整 plan（与前端 `planApi.placeUpsert` 现有声明一致，零前端改动）；
   - `POST /journeys/plan/place/delete`：请求体 = `journeyId + clientId`，删除地点 + 联动删占位记录（把 `prunePlanPlaceEntries` 从 putPlan diff 路径挪到单点路径复用）。
2. **plan/save 降级为纯全量场景**（排序、批量初始化、预算），前端 `pushRemote` 保留；`pushPlaceRemote`/`pushPlaceDeleteRemote` 改为直连单点接口，**移除 catch 降级**（404 降级吞错误，应显式暴露）。
3. **清理 plan/checks 残留**：`plan/save` 与 `plan/toggleCheck` 的 checks 双写彻底下线，进度统一走 checklist 模块。
4. **entries/sync 可选收敛**：如产品需要实时单条新增，可加 `entries/create`；纯离线场景可维持 sync。
5. **expense**：若存在独立记账需求，新增 `POST /journeys/expense/create`（关联 journeyId）；否则维持内嵌。
