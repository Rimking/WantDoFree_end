## 一、背景与问题（Why）

### 1.1 现状

`TravelIdentityDict` + `UserIdentity` 已存在，用户可在 `ProfileEditTravelCard` 选择最多 3 个"旅行身份"（背包客/美食猎人/度假党/摄影控/人文探索/户外徒步/亲子同游）。但经代码核查，**该数据在已上线功能中无任何消费方**——选完存库后，分享、游记、首页、统计均不读取。属于"死数据"。

### 1.2 问题

1. **用户付出无回报**：用户花时间选择身份，却永远看不到它生效，会产生"这功能坏了"的错觉。
2. **错失成长激励**：旅行类产品天然适合用徽章做"成就反馈"，这是提升留存和分享率的高杠杆手段。
3. **社交货币缺失**：分享图上没有"人设标识"，别人看到分享图无法感知"这是个爱拍照的人/美食家"，削弱了病毒传播。

### 1.3 目标

将"静态身份标签"升级为**动态成就徽章体系**：

- 用户的选择 = "我想成为谁"的**目标设定**
- 系统根据真实旅行行为**自动判定解锁**并展示等级
- 徽章成为贯穿"个人资料→游记→分享"的**社交货币**

## 二、目标与用户故事

### 2.1 产品目标

| 目标 | 衡量方式 |
|------|---------|
| 让身份选择产生价值 | 选了身份的用户，徽章解锁率 ≥ 80% |
| 提升分享传播力 | 带徽章水印的分享图占比 ≥ 60% |
| 提升次日/7日留存 | 徽章用户 7 日留存比无徽章用户高 ≥ 10pp |
| 增加回访钩子 | 解锁弹窗点击"炫耀一下"率 ≥ 25% |

### 2.2 用户故事

```
作为 旅行记录用户，
我希望 选择旅行身份后，系统能根据我的真实旅程自动给我颁发对应徽章，
以便 感受到自己的旅行风格被认可，并愿意展示和分享。

作为 频繁记录的用户，
我希望 看到自己累计解锁的成就徽章（如"记录达人""城市漫游者"），
以便 获得持续使用产品的动力。

作为 收到朋友分享图的人，
我希望 从分享图上看到对方的旅行人设徽章，
以便 快速理解"这是个怎样的人"，并产生"我也能玩"的念头。
```

## 四、数据契约

### 4.1 现有可复用字段（已确认，无需新建业务表）

| 来源 | 字段 | 用途 |
|------|------|------|
| `journeys` | `status`, `startDate`, `endDate`, `destinations[]`, `companions[]`, `themeTags[]`, `budgetAmount`, `isPublic` | B01/B03/B08/B14/B15/B16/B17/B18/B20 判定 |
| `entries` | `type`, `recordedAt`, `dayIndex`, `location`, `media`, `expenses` | 全部记录级判定 |
| `entry.location.name` | 关键词匹配（岛/海/雪/山/古镇/馆…） | B09/B10/B11/B19 判定 |
| `entry.expenses` | `amount`, `category` | B02/B07/B16/B17/A07 判定 |
| `entry.content` | 长度 + 关键词（吃/文化/我们…） | B02/B05/B07 判定 |
| `user` 统计 | `footprintCities`, `tripCount` | 跨旅程汇总 |

### 4.2 必要的数据模型扩展

仅扩展 `user_identity` 关联表（**不新建表**）：

```sql
ALTER TABLE user_identity
  ADD COLUMN unlocked_at TIMESTAMP NULL,
  ADD COLUMN level INT NOT NULL DEFAULT 0,   -- 0=未解锁 1=铜 2=银 3=金
  ADD COLUMN progress JSON NULL;             -- {current,target,percent,label}
```

新增徽章字典表（存放 30 枚徽章的元数据，含基础/成就分类）：

```sql
CREATE TABLE badge_dict (
  code VARCHAR(32) PRIMARY KEY,        -- 'backpacker' / 'foodie' / 'first_record' ...
  name VARCHAR(32) NOT NULL,
  category VARCHAR(16) NOT NULL,      -- 'base' | 'achievement'
  icon VARCHAR(64),
  bronze_cond JSON,                    -- {metric,target,label}
  silver_cond JSON,
  gold_cond JSON,
  eval_trigger VARCHAR(32)             -- 'record'|'share'|'travelogue'|'journey'|'daily'
);
```

## 五、技术方案

### 5.1 判定引擎（事件驱动，不跑批）

| 触发事件 | 检查徽章 |
|---------|---------|
| 保存 `entry` | B01-B06, B12-B13, B19, A01-A02, A07 |
| 生成游记(DraftBox) | A03, B04(金) |
| 完成分享 | A04, A09 |
| 创建/完成 `journey` | B01, B03, B07-B08, B14-B18, B20, A05, A08, A10 |
| 每日定时(低频) | A06（按周结算连续） |

核心函数：
```typescript
evaluateBadges(userId, trigger):
  candidates = SELECT * FROM badge_dict WHERE eval_trigger = trigger
  for b in candidates:
    progress = computeProgress(b, userId)   // 纯函数，读现有表
    if progress.level > stored.level:
      unlock(b, progress.level)             // 写 user_identity + 发解锁事件
```

## 六、消费场景

1. **个人资料卡**：最近 5 枚徽章横排，点击进徽章墙
2. **分享图水印**：取最高等级身份徽章，如「📷 摄影控 · 渡清川」
3. **游记详情**：标题旁挂该旅程相关徽章（如 杭州三日游 🎒📷）
4. **解锁弹窗**：触发时弹出，提供"炫耀一下"分享入口（病毒传播）

## 八、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 关键词匹配误判（如"海"字地名非海岛） | 错误解锁 | 维护关键词白名单 + 人工复核高频误判 |
| 判定逻辑性能 | 每次记录查多表 | 用聚合查询 + 缓存用户统计快照 |
| 用户刷徽章（如频繁建空旅程） | 数据失真 | 仅 `finished` 状态旅程计入；记录数需 `content` 非空 |

## 九、Non-goals（明确不做）

- ❌ 徽章交易/赠送/排行榜竞争（避免焦虑）
- ❌ 徽章绑定付费权益（MVP 不跟会员挂钩）
- ❌ 徽章过期/降级（解锁即永久）
- ❌ 用户自定义徽章
- ❌ 实时全站排行

## 十一、验收标准

1. 用户完成首条记录 → 自动解锁 A01「初出茅庐」+ 弹窗
2. 用户在资料页看到 20 枚基础徽章（已解锁亮态 / 未解锁灰态 + 进度）
3. 用户生成长图 → 底部显示最高等级身份徽章水印
4. 所有判定条件仅基于现有 Entity 字段，`user_identity` 仅扩展 3 列，新建 `badge_dict` 字典表
5. 徽章墙 30 枚全量展示，每枚显示名称/图标/等级/进度百分比
