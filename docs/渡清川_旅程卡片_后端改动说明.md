# 渡清川 · 旅程卡片统一规范 — 后端改动说明

> 配套：`渡清川_旅程卡片_统一规范.html`、`渡清川_旅程卡片_改动说明_handoff.md`  
> 前端已按统一竖版卡片改完；本文只列**需要后端配合**的字段与行为。  
> 日期：2026-07-23

---

## 结论

| 优先级 | 是否必须 | 说明 |
|--------|----------|------|
| P0 | **建议改** | 列表返回可直接展示的 `displayStatus`（含派生「即将出发」）与 `planProgress` |
| P1 | 可选增强 | `todayPlaceCount`、草稿态、按展示态筛选 |
| — | **可不改** | `placeCount` / `expenseTotal` / `days` 等已有字段够用；前端可继续本地算「即将出发」与完成度 |

**前端现状**：已用本地规则 `resolveJourneyStatus`（出发日 ≤ 3 天 → `departing`）+ 计划 checklist 算完成度。  
**为何仍建议后端改**：避免前后端两套规则漂移；列表页不必再拉 plan 才能画底栏。

---

## 一、现有接口够用的部分（无需动）

列表项已有、前端卡片可直接用：

| 字段 | 卡片用途 |
|------|----------|
| `cover` / `coverUrl` | 图区 16:9 |
| `title` | 标题 |
| `startDate` / `endDate` | 元信息日期区间、已完成「N 天」 |
| `placeCount` | 元信息「N 个地点」、已完成底栏地点 |
| `expenseTotal` / `totalExpenseCent` | 已完成底栏花费 |
| `status` = `planned` / `ongoing` / `finished` | 持久化三态（与写入契约一致） |

交互（记一笔 / 看地图 / 手帐 / 分享）仍走现有详情、地图、花费、攻略接口，**不新增写接口**。

## 二、建议改动（P0）

### 2.1 列表返回展示态 `displayStatus`

在 `GET /journeys`、`GET /journeys/:id` 响应中增加（或扩展）展示用状态。

**推荐枚举（英文，与前端对齐）：**

```text
planning | departing | ongoing | finished | draft
```

| 值 | 中文 | 计算规则（建议后端统一） |
|----|------|--------------------------|
| `draft` | 草稿 | 持久化为草稿，或未满足「可发布」条件（见 P1） |
| `planning` | 规划中 | 持久化 `planned`，且距 `startDate` **> 3 天**，且未结束 |
| `departing` | 即将出发 | 持久化 `planned`，且 `startDate` 落在 **今天 ～ 今天+3 天（含）**，且今天 ≤ `endDate` |
| `ongoing` | 进行中 | 持久化 `ongoing` |
| `finished` | 已完成 | 持久化 `finished` / `ended` |

**写入不变**：`POST/PATCH`、`POST .../status` 仍只接受 `planned | ongoing | finished`（`departing` 不落库，只读派生）。

兼容方案二（二选一即可）：

- A. 新增字段 `displayStatus`，保留原 `status` 为持久化值  
- B. 列表的 `status` 直接返回五态（含 `departing`），文档写明「读模型」；写接口仍只收三态  

推荐 **A**，读写语义更清晰。

示例：

```json
{
  "id": "...",
  "status": "planned",
  "displayStatus": "departing",
  "startDate": "2026-07-25",
  "endDate": "2026-07-30",
  "planProgress": 30,
  "placeCount": 4,
  "expenseTotal": 0
}
```

### 2.2 `planProgress`（0–100）

底栏「完成度」统一取该字段，与 `displayStatus` **正交**（各态都可有完成度）。

**建议算法（与产品确认后固化）：**

```text
若 plan.checks 为空 → 0
否则 → round( doneChecks / totalChecks * 100 )
```

「规划中 · 已定」可与完成度同源：`confirmedCount = doneChecks`（见 P1），或前端继续用 progress 推导。

列表接口带上该字段后，首页可不依赖先拉 `/plan` 也能画齐卡片底栏。

## 三、可选增强（P1）

### 3.1 `todayPlaceCount`（进行中底栏「今日地点」）

| 字段 | 类型 | 说明 |
|------|------|------|
| `todayPlaceCount` | number | 当天计划内地点数；无日程模型时可暂等于 `placeCount` 或 `0` |

前端当前用 `placeCount` 顶替，数字可能偏大，有日程/dayIndex 后再精确。

### 3.2 草稿 `draft`

卡片规范含草稿态（继续编辑 / 删除，底栏 `—`）。若产品要草稿：

- 持久化增加 `draft`，或 `status=planned` + `isDraft=true`
- 列表 `displayStatus=draft`
- 筛选：草稿是否进「全部」、是否单独 Tab，由产品定

无草稿产品线则可忽略，前端草稿槽位闲置即可。

### 3.3 列表筛选支持展示态

现有：

```http
GET /journeys?status=planned|ongoing|finished
```

建议增加（或文档约定）：

```http
GET /journeys?displayStatus=departing
GET /journeys?displayStatus=planning
```

说明：`status=planned` 会同时包含「规划中 + 即将出发」；若 Tab「即将出发」走服务端筛选，必须用 `displayStatus`。

前端目前是拉全量后本地 `resolveJourneyStatus` 过滤，**短期可不改筛选参数**。

### 3.4 规划中「已定」计数（可选）

| 字段 | 类型 | 说明 |
|------|------|------|
| `confirmedCount` | number | 已勾选 checklist 数，对应底栏「已定」 |

无此字段时前端用 plan.checks 或仅用 `planProgress` 展示。

---

## 四、前端卡片字段对照（后端按此对齐即可）

| 展示态 | 角标 | 底栏 | 优先依赖字段 |
|--------|------|------|----------------|
| ongoing | 进行中 | 今日地点 / 完成度 | `todayPlaceCount?`, `planProgress` |
| departing | 即将出发 | N天后出发 / 完成度 | `startDate`, `planProgress` |
| planning | 规划中 | 已定 / 完成度 | `confirmedCount?`, `planProgress` |
| finished | 已完成 | 天数 / 地点 / 花费 | `startDate`+`endDate` 或 `days`, `placeCount`, `expenseTotal` |
| draft | 草稿 | — / — | `displayStatus=draft` |

按钮文案与跳转由前端映射，**后端无需返回按钮配置**。

---

## 五、验收建议

1. 造一条 `planned` 且 `startDate` 在 3 天内的旅程 → `displayStatus === "departing"`。  
2. 造一条 `planned` 且出发日 > 3 天 → `displayStatus === "planning"`。  
3. `checks` 2/4 完成 → `planProgress === 50`。  
4. `finished` 项带 `placeCount`、`expenseTotal`（分）正确。  
5. 列表不强制嵌套完整 `plan` 对象（有 `planProgress` / `placeCount` 即可）。

## 六、工作量粗估

| 项 | 估时 |
|----|------|
| `displayStatus` 派生 + 列表/详情透出 | 0.5–1d |
| `planProgress` 聚合进列表 | 0.5d |
| 筛选 `displayStatus`、草稿、`todayPlaceCount` | 按需，各 0.5d 量级 |

**最小交付**：只做 §2（`displayStatus` + `planProgress`），即可与当前统一卡片规范对齐；其余前端可先降级计算。
