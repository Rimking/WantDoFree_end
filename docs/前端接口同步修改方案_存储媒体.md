# 前端接口同步修改方案（存储 / 媒体体系）

> 日期：2026-07-24  
> 对齐后端：《渡清川_存储与后端服务体系设计.html》落地结果  
> 服务前缀：`/api/v1`，鉴权：`Authorization: Bearer <token>`  
> 目标：前端上传契约与媒体响应与后端一致；其它业务接口尽量少动

---

## 1. 要不要改？结论先看

| 范围 | 是否必须改 | 说明 |
|------|------------|------|
| 图片 / 语音 **上传** | **必须** | 收敛到 `prepare → upload → confirm` |
| **头像 / 旅程封面** 上传 | **必须**（若已接上传） | 同一契约，`ownerType` 不同 |
| 时间线 **读** `entries` | **建议** | 已内联 `media[]`，字段 `kind` 变为 `image\|audio` |
| 记录 sync / 旅程 / 目的地 / 清单 / 统计 | **可不改** | 无破坏性变更；sync 仍可传已上传 URL |
| 旧 `GET /media/upload-url` | **应废弃** | 后端仍兼容，但勿新写 |

**一句话**：凡「选文件 → 上传到云/本地 → 落库」的路径都要改；纯 CRUD 业务接口可先不动。

---

## 2. 新旧对照

### 2.1 上传链路

| 步骤 | 旧（废弃） | 新（统一） |
|------|------------|------------|
| 1 | `GET /media/upload-url?key=&kind=photo\|voice` | `POST /media/prepare` |
| 2 | `wx.uploadFile` / `PUT` 到预签名 URL（多为 mock） | `wx.uploadFile` 到 `uploadUrl`（local 为后端地址；cos 为云地址） |
| 3 | `POST /media/confirm` `{ entryId, kind, url, size }` | `POST /media/confirm` `{ mediaId, confirmToken }` |
| 回读 | 依赖 CDN / mock URL | local：`/api/v1/files/yyyy/mm/dd/xxx.ext`（需带 Token） |

### 2.2 kind 枚举

| 场景 | 旧 | 新（规范） | 兼容 |
|------|----|------------|------|
| 图片 | `photo` | `image` | 请求仍可传 `photo`；响应有 `legacyKind: "photo"` |
| 语音 | `voice` | `audio` | 请求仍可传 `voice`；响应有 `legacyKind: "voice"` |

前端新建代码请一律用 **`image` / `audio`**；读旧字段时用：

```ts
const isImage = (k: string) => k === 'image' || k === 'photo';
const isAudio = (k: string) => k === 'audio' || k === 'voice';
```

### 2.3 归属 ownerType（必填）

| ownerType | ownerId | 用途 |
|-----------|---------|------|
| `entry` | 记录 id | 时间线条目附件 |
| `avatar` | 当前用户 id | 头像 |
| `journey_cover` | 旅程 id | 旅程封面 |
| `guide` | 攻略 id | 攻略图（预留） |
| `destination` | 目的地 id | 目的地相册（预留） |

> 注意：`prepare` 时 **owner 必须已存在**（entry / journey 等）。新建记录建议：先 sync 出 entry，再 prepare；或先上传到临时归属策略由产品定（当前后端要求 owner 存在）。

## 3. 新接口契约（前端实现依据）

### 3.1 `POST /media/prepare`

**请求**

```json
{
  "ownerType": "entry",
  "ownerId": "entry-uuid",
  "kind": "image",
  "mime": "image/jpeg",
  "sizeBytes": 204800,
  "durationSec": 18,
  "sortOrder": 0
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| ownerType | ✅ | 见上表 |
| ownerId | ✅ | 归属 id；avatar 时 = 当前 userId |
| kind | ✅ | `image` \| `audio`（兼容 photo/voice） |
| mime | ✅ | 见白名单 |
| sizeBytes | ✅ | 字节数；图片 ≤10MB，音频 ≤30MB |
| durationSec | 音频建议 | 用于配额预检 |
| sortOrder | 否 | 同 entry 多图排序 |

**MIME 白名单**

- 图片：`image/jpeg`、`image/png`、`image/webp`
- 音频：`audio/m4a`、`audio/mp3`、`audio/mpeg`、`audio/aac`、`audio/mp4`、`audio/x-m4a`

**响应**

```json
{
  "mediaId": "uuid",
  "uploadUrl": "http://127.0.0.1:3000/api/v1/media/local-upload",
  "method": "POST",
  "headers": {},
  "fields": {
    "mediaId": "uuid",
    "confirmToken": "jwt..."
  },
  "confirmToken": "jwt...",
  "storageKey": "2026/07/24/uuid.jpg",
  "driver": "local"
}
```

- `driver=local`：`method=POST`，`uploadUrl` 指向本后端；formData 必须带 `fields` + 文件字段名 **`file`**
- `driver=cos`：`method=PUT`，直传云；`headers` 可能含 `Content-Type`；`fields` 通常为空

### 3.2 上传（小程序）

```js
// local / cos 共用：以 prepare 返回为准
wx.uploadFile({
  url: prepare.uploadUrl,
  filePath: tempFilePath,
  name: 'file',                    // local 必填字段名
  header: {
    Authorization: `Bearer ${token}`,
    ...(prepare.headers || {}),
  },
  formData: {
    ...(prepare.fields || {}),     // mediaId + confirmToken（local）
  },
});
```

COS 且 `method=PUT` 时，用 `wx.request` 读文件 ArrayBuffer 再 PUT（按你们现有 COS 工具封装即可）；**不要写死 local 或 cos 分支业务逻辑以外的第二套 confirm**。

### 3.3 `POST /media/confirm`

**请求（新）**

```json
{
  "mediaId": "uuid",
  "confirmToken": "jwt...",
  "durationSec": 18,
  "width": 4032,
  "height": 3024
}
```

**响应（媒体 DTO）**

```json
{
  "id": "uuid",
  "ownerType": "entry",
  "ownerId": "...",
  "kind": "image",
  "legacyKind": "photo",
  "url": "/api/v1/files/2026/07/24/uuid.jpg",
  "thumbUrl": null,
  "mime": "image/jpeg",
  "sizeBytes": 204800,
  "size": 204800,
  "width": null,
  "height": null,
  "durationSec": null,
  "sortOrder": 0,
  "status": "active",
  "driver": "local"
}
```

- confirm 幂等：已 `active` 再调一次仍返回同一 DTO
- `avatar` confirm 成功后后端会写 `users.avatar`
- `journey_cover` confirm 成功后会写 `journeys.cover`

### 3.4 `GET /files/:y/:m/:d/:file`

- 仅 **local** 驱动需要；展示图片时若 `url` 以 `/api/v1/files` 开头，请求必须带 Bearer（或把完整 URL 交给已带鉴权的下载组件）
- 生产环境会校验文件归属；开发环境主要防路径穿越

### 3.5 时间线响应（建议对齐）

`GET /journeys/:id/entries` 单条示例中的 `media`：

```json
{
  "id": "entry-uuid",
  "type": "photo",
  "content": "...",
  "media": [
    {
      "id": "m1",
      "kind": "image",
      "legacyKind": "photo",
      "url": "/api/v1/files/...",
      "thumbUrl": null,
      "width": null,
      "height": null,
      "durationSec": null,
      "sortOrder": 0,
      "sizeBytes": 220000
    }
  ],
  "images": ["..."],
  "audioUrl": null,
  "voice": null
}
```

前端展示层：

- 优先用 `media[]`（按 `sortOrder`）
- 兼容保留 `images` / `audioUrl` / `voice`（后端仍返回）

| # | 任务 | 说明 |

## 5. 推荐前端流程（伪代码）

### 5.1 给已有 entry 追加一张图

```ts
async function addPhotoToEntry(entryId: string, filePath: string, sizeBytes: number) {
  const prep = await api.post('/media/prepare', {
    ownerType: 'entry',
    ownerId: entryId,
    kind: 'image',
    mime: 'image/jpeg',
    sizeBytes,
  });

  await uploadByPrepare(prep, filePath); // 内部 wx.uploadFile / PUT

  const media = await api.post('/media/confirm', {
    mediaId: prep.mediaId,
    confirmToken: prep.confirmToken,
  });

  // 可选：刷新时间线；或 patchRecord 把 images 同步成最新
  return media; // { id, url, kind: 'image', ... }
}
```

### 5.2 新建记录（建议顺序）

```
1. （可选）仅文字可先 sync 出 entry
2. 对每张图 / 每段语音：prepare → upload → confirm，收集 url
3. POST /journeys/:id/entries/sync
   body.media = [{ url, kind: 'photo'|'image', size }]  // 仍兼容
```

若产品要求「先选图再创建记录」：需先有 entry（可先建空草稿 entry），或产品与后端另定临时 owner——**当前后端不支持无 owner 的悬空上传**。

### 5.3 头像

```ts
const prep = await api.post('/media/prepare', {
  ownerType: 'avatar',
  ownerId: currentUserId,
  kind: 'image',
  mime: 'image/jpeg',
  sizeBytes,
});
await uploadByPrepare(prep, filePath);
const media = await api.post('/media/confirm', {
  mediaId: prep.mediaId,
  confirmToken: prep.confirmToken,
});
// media.url 已写入用户 avatar；刷新 /me 或 /user/profile
```

## 6. 环境差异（前端几乎无感）

| 环境 | STORAGE_DRIVER | 前端差异 |
|------|----------------|----------|
| 本地开发 | `local` | `uploadUrl` 指向本机；展示 `/api/v1/files/...` |
| 生产上云 | `cos` | `uploadUrl` 为 COS；展示 CDN/COS URL |

**前端不要写死「永远 POST 到本机」或「永远 PUT COS」**，一律以 prepare 返回的 `method` / `uploadUrl` / `headers` / `fields` 为准。

配置侧仅后端改 `.env`，前端契约不变。

## 8. 联调验收清单（前端）

- [ ] local 下选图：prepare → uploadFile → confirm 成功，时间线出现图
- [ ] 超配额：prepare 返回 `QUOTA_EXCEEDED`，UI 引导容量包
- [ ] 非白名单 MIME / 超大文件：前端拦截 + 后端 400
- [ ] `/api/v1/files/...` 带 Token 可显示；不带 Token 失败可接受（当前需登录）
- [ ] 改后端 `STORAGE_DRIVER=cos`（即使 COS 仍为占位）前端无代码改动能走到 confirm（或明确 mock 失败提示）
- [ ] 头像 / 封面走同一套上传后，`/me`、旅程详情封面刷新正确
- [ ] 旧机型 / 旧包：若仍打旧 confirm，不致命（后端兼容），但发版后应切新包
